# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TrackerTFT (TFT Comp Tracker): a static, no-build web app for Teamfight Tactics. The user types player names, then links each of the 8 players to the meta compositions they appear to be playing on a "scout sheet": a matrix of comps (rows) × players (columns). There is no package.json, bundler, linter, or test suite.

## Running

Serve the repo root over HTTP (ES modules and `fetch('Data/MetaSnapshot.json')` don't work from `file://`), e.g. `python -m http.server 8000` and open `http://localhost:8000`. `index.html` uses absolute `/favicon.svg`, `/favicon.ico` and `/apple-touch-icon.png` (the Lobby Scan radar logo, also in the header's brand), so the root must be the site root.

## Architecture

- **Entry points** (both `type="module"` in `index.html`): `Scripts/mainScreen/domContentLoad.js` (DOMContentLoaded wiring: region selector remembered in `localStorage`, player search and the `/` shortcut, Solo/Double Up switch, reset, copy names) and `Scripts/mainScreen.js` (startup: `initViewTabs()`, `applyQueryParams()` → `tryLoadDefaultData()`).
- **Modules query the DOM at import time** (e.g. `document.getElementById('players')` in `players.js`, `'compos'` in `dataLoader.js`/`matrix.js`, `'itemPicker'` in `itemPicker.js`), so they rely on `index.html` script placement and there are circular imports between `players.js`, `matrix.js`, `dataLoader.js`, `compSearchBar.js`, `itemPicker.js` and `shareUrl.js`. Be careful when moving code between these files.
- **Shared state** lives in module-level exports rather than a store: `links` (`{compo, player, pivot}` in `matrix.js`; `pivot`: false is "Confirmed", true "Possible"; a click links a cell as confirmed or unlinks it, a player on 2+ comps has them all as possible, and a right-click switches confirmed ⇄ possible, confirming dropping the player's other comps) is the source of truth for the matrix cells, comp states and share URLs, and `renderLinks()` repaints everything derived from it (then fires `tft:linkschange`); `duelsCache` in `players.js`; `metaSnapshotData`, `unitImageMap`, `unitCostMap`, `items` in `dataLoader.js`.
- **Two data sources:**
  1. `Data/MetaSnapshot.json` — one entry per set, keyed by set name (`"SET 18"`), generated by the backend; its full format is documented in TFT_Versus's CLAUDE.md ("MetaSnapshot format"). In short: `comps` (TFT Flow's; each with `champions` + their `build`, the full `board`, `plannerCode`, `url`), `champions` (units with `traits`, `role`, item tiers `{base, games, core, S, A}`, `variants` for `Adaptor` champions, `artifacts`/`emblems`; the set summary drawer shows these), `conditions` (curated artifact/emblem/radiant lists per comp), the `items` catalog, `components`, `recipes`, `patch`, `status` (`live`/`pbe`, with PBE sets on stand-in tiers) and `compSources` (`tftflow`, which is the set's own `comps`/`conditions`, plus `metatft`, `tactics` and `tftacademy`, each with its own `comps`/`conditions` and, for stat sources, per-comp `stats`). Loaded by `dataLoader.js`, cached in `sessionStorage` under a versioned key (`metaSnapshot:v5`; bump it when the format changes, and hard-reload/new tab after changing the file). The live set is the default (older frontends use the last key, so the backend writes the live set last); the set dropdown is built from the keys, labels PBE sets and is hidden when there is only one set, and `getCurrentSetData()` plus the `tft:setchange` document event expose the selected set to other views.
  2. The external **TFT Versus** backend (`https://api.trackertft.com/api`, an OCI VM, endpoints in `Scripts/config.js`), called only through `fetchFromTFTVersusAPI` in `Scripts/tftVersusHandler.js`. Errors come back as `{detail, status, retryAfter}` (real HTTP status attached; `retryAfter` from the 429's `Retry-After` header); callers such as `searchCurrentGame.js` check `detail`/`status` rather than catching. Requests are plain GETs (no `Content-Type`), so they skip the CORS preflight. The search loads the live game and the player's card in parallel and retries 429s with a countdown; the versus checks (`/find`) run 3 at a time, and a rate-limited one shows its countdown in place and retries by itself. `tftVersusHandler.js` also builds all image URLs (champions, items, augments from MetaTFT's CDN by lowercased apiName; traits and ranked icons from CommunityDragon).
- **Lobby UI (scout sheet):** `#players` is `display: contents` inside the sticky `.matrix-head` grid, so each `.item.player` (`players.js`) is a column header (avatar from the live game's `profileIconId`, name, rank, edit/duel actions); Double Up `.team-container`s span two columns. Each `.item.compo` row (`dataLoader.js`) is a grid with the comp cell (carries with their build, core items ringed, 3★ targets starred), and 8 `.link-cell`s (click links the column's player, handled by delegation in `matrix.js`). Each comp has a `plannerCode` (its board as an in-game Team Planner code: `02`, 10 slots of 3 hex digits from CommunityDragon's `team_planner_code`, `000` empty, then `TFTSet18`), copied by a button that shows on row hover. Rows show the source's own builds under each itemized unit (`build`: items, artifacts, emblems, radiants) and the rest of the final `board` smaller after them; only carries (`data-carry`: the main champion and itemized non-tanks) count as taken or contested. `matrix.js` sets each row's `data-state` (`open` = uncontested, shown as a star before the name / `shared` = a carry is taken by another player / `linked` / `crowded` = 2+ players) and the "Contested carries" card, which stays right under the item picker in the side panel. `compSearchBar.js` owns row visibility in one place (`applyCompVisibility()`: tags OR, comp-name text while no tag is set, the All/Uncontested/Linked view; linked comps stay visible except under Uncontested, which only shows `open` comps) and tier header counts. `itemPicker.js` is the side panel: up to 3 distinct components (recipes they complete together weigh 1, half-covered recipes 0.35) plus toggled items/artifacts/emblems, which are also draggable onto players; it lists suggested comps, shows matched items on rows and fades the rest. `compSource.js` owns the comp source: the "Comps from …" menu in the matrix head (hidden with one source; each source shows its site's favicon, kept in `img/sources/`, and the head links to the site), a small print line with the data's patch and when it was gathered (`updatedAt`, UTC, per source and per set) plus a note when the source has no placement stats, a confirmation before switching when comps are linked (links are cleared, players and items stay), MetaTFT by default (TFT Flow when a set has no MetaTFT comps, e.g. the PBE), the user's pick remembered in `localStorage` and always carried by share URLs as `source`. `sourceView(set, id)` is the set as the lobby sees it (the source's `comps`/`conditions` over the set's data); `getCurrentSetData()` returns that view, and a switch rebuilds the lobby and fires `tft:sourcechange`. Rows of stat sources show a compact stats line; `compStatCard.js` shows the full card (with the 1st-8th spread) on hover. `compFit.js` is the shared fit rule used for every suggestion: item → a carry builds it (1) or rates it Core/S/A (1/0.8/0.5); artifact / emblem / radiant → TFT Flow's curated `conditions` for that item (tier weight S 1 … D 0.25, holder from the snapshot; comps it doesn't list don't want it), with the old heuristics only for items no list covers. `playerItems.js` owns each player's box of up to 6 items (`data-items` on the player element; drop from the picker, drag between players, click to remove): it marks the player's top 3 unlinked potential comps as `.hint` cells, fills the "Potential comps" card (with each item's holder) for the last player touched, and badges artifact/emblem holders on the comps the player is linked to (repainted on `tft:linkschange`). `searchCurrentGame.js` runs search → summary → live game → populates players. A player's ⚔ opens the versus (`versus.js`, `css/versus.css`, classes prefixed `vs-`): a Glance card under their column (a bottom sheet on phones: record, your last 10 finishes against them, averages, contested %; no aggregate of the opponent's champions, by design) and a full Report (current set by default, other sets and All sets on demand; a placements line chart, or the finishes grid by default past 10 games; every game with both final boards, units you both played marked, the winner's side tinted, Little Legends from CommunityDragon's companions list, each player's rank then, and the contested % as a traffic light). Both come from one call to the backend's `/versus` (with `ranks_pending` the frontend asks once more after 8s). Clicking a game expands its whole lobby, fetched only on that click (`/match/{id}`) and kept for the session. What these endpoints guarantee is in TFT_Versus's CLAUDE.md ("Frontend contract"). `components.js` still holds the old duel modal (`openDuelModal`, `modal.css`, `match-history.css`), no longer opened from the lobby.
- **Accounts** (`Scripts/account/`, `css/account.css`, classes prefixed `acct-`): sign in with email + password, Google or Riot (RSO); the backend's `/api/auth` owns everything (cookies, tables, bot protection: see "Auth" in TFT_Versus's CLAUDE.md). `netlify.toml` proxies `/api/auth/*` to the backend so the HttpOnly session cookie is first-party; `AUTH_API_URL` is always the relative `/api/auth`, so the site must be served by Netlify or by the backend itself (`FRONTEND_DIR` serves this repo on :5000, and `config.js` then uses `/api` for everything). Other API routes get a short-lived signed `api_token` from `/me`, sent as `Authorization: Bearer` by `authHeaders()` (`session.js`, which also holds the user, fires `tft:userchange` and gates features with `hasFeature()`). `dialog.js` is the one account dialog (views signin, signup, verify, forgot, reset, settings, password, riot; buttons for providers the backend hasn't configured show "Soon"; Turnstile loads only when configured; a honeypot field), `header.js` the "Sign in" button / avatar chip and menu in `#accountSlot`, and it reports `?auth_error=` from Google/Riot redirects. Every account must link a verified Riot ID: while `/me` says `needs_riot_link` the backend grants no plan feature, `header.js` opens the dialog on the Riot ID step and `dialog.js` won't close (only sign out or account settings). Linking a Riot ID without RSO asks the user to set a given default profile icon. Plans are `free`/`premium`; features come from the backend (`versus_pro` is public for now). `.player-search` stays hidden unless `hasFeature('live_game')`, and `fetchLiveGame` sends `authHeaders()`; non-VIP accounts wait 30s between searches (the button counts down; the backend enforces it too). While Riot's spectator API is off, VIP accounts (`hasFeature('name_lookup')`, switchable in the backend) can rename a column with the name seen in game: `nameLookup.js` (listening for `tft:playerrename` from `players.js`) asks `/opponents` who it is among their own games; one match fills in the Riot ID, several open a picker under the column (`.vs-pick`, styled as the Glance card), and a typed `Name#TAG` skips the lookup. Either way `checkVersus()` (`searchCurrentGame.js`) runs the usual `/find` check against the signed-in Riot ID, on its linked server. Signed in with a verified Riot ID, the first solo column defaults to that Riot ID instead of "YOU" (`ownRiotId()` in `players.js`; share URLs still compare against "YOU", so the owner's name is written). The sign-in and sign-up views put the email form first and Google/Riot below it. `legal.html` is the terms and privacy notice; keep it in sync with what the backend stores.
- **Share URLs** (`shareUrl.js`): state is serialized into query params — `Player1..8`, `Player{N}Comps` (comp indexes, `*` marks the main comp) and `Player{N}Items` (item apiNames), both set-specific and cleared when the set changes (comps also when the source changes), `set`, `source`, `mode` (only `mode=double` is written; absent means solo). `applyQueryParams()` runs before data loads; `linkPlayersToCompsFromQuery()` re-links after comps render.
- **Solo/Doubles mode:** the hidden `#color_mode` checkbox stays the source of truth (share URLs and live-game search set it); `toggleDoubleUpMode()` flips `body.double-up`, syncs the header switch and rebuilds the player columns.
- **Views:** `index.html` has a tab bar (`#view-tabs`) in the app header switching `#tracker-view` (the lobby) and `#transitions-view` (shown as "Set Summary"). `viewTabs.js` owns switching, keeps the view in the URL hash (`#summary`) and lazy-imports `transitionsView.js` on first open. The set summary follows the lobby's set, and has its own Live/PBE dropdown (via `getSnapshotSets()`) while more than one set is published, which doesn't touch the lobby.
- **Transitions view** (`transitionsView.js`, `css/transitions.css`, classes prefixed `tv-`): early→late champion transitions by shared S/A ("ideal") items. It is built from the selected set's `champions`/`recipes`/`components` in MetaSnapshot (no data of its own) and derives AD/AP/Hybrid and tank item classes from who rates each item S/A. Entries are keyed by name, or `name|AD` / `name|AP` for `Adaptor` champions, which get one entry per build (from `variants`, or their tiers split by item class on older snapshots) and an AD/AP switch in the drawer. It reads `links` to mark champions taken by lobby players, and its drawer calls `addCompFilter()` (`compSearchBar.js`) to jump to the tracker filtered by a champion.
- **CSS** is aggregated by `css/main.css`: `variables.css` (light "scout sheet" tokens; the only color is game meaning: unit cost `--c1..5`, tiers `--t-*`, player colors, open/shared/contested states; legacy token names are mapped for the set summary view, and `#popupOverlay` restores the old dark palette so the duel modal is unchanged), `base.css`, `shared.css` (spinner, mini rank, duel button, modal rank cards, toast), `modal.css`, `match-history.css`, `lobby.css` (header, sheet, matrix, side panel, breakpoints at 1440/1180/900/640px that shed the least important parts first: the rest of the board, the matched-items strip, then on phones item boxes, style/ranks and carries beyond the third; the duel modal adapts instead of hiding) and `transitions.css`. Player colors (`CONFIG.colors`) and tier colors are picked to read on white.

## Data updates

`Data/MetaSnapshot.json` is regenerated by a bot (`Zeroclbot`, commit messages like "Update MetaSnapshot (… comps) for sets: 18") and accounts for most commits. The generator, its sources, the publishing schedule and the item tier rules live in the backend repo (`TFT_Versus`, see its CLAUDE.md). The backend checks every hour and publishes only when due. The frontend shows the Core item tier as an outlined gold badge and a gold ring on item icons. Treat the file as generated and avoid hand-editing or reformatting it; keep new fields additive, since the bot also publishes to `main` where the older frontend reads it. `riot.txt` is the Riot API domain-verification file; leave it in place.

## SEO and crawlers

The site lives at `https://trackertft.com` (Netlify DNS; `netlify.toml` 301s the `netlify.app` address there, since sign-in only accepts that origin). `index.html` carries the title, description, canonical, Open Graph/Twitter tags (image `img/og-image.png`, 1200×630), a `WebApplication` JSON-LD block and a visually hidden `<h1>`; keep them accurate when features change. `sitemap.xml` lists the pages. `robots.txt` welcomes search engines and AI search/assistant crawlers but disallows AI training crawlers (same list as the backend's `constants/bot_constants.py`) and `/api/`; don't block `Data/`, which Google needs to render the page.
